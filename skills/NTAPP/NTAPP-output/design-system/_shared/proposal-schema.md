# Proposal Schema — Design System Delta Report

**Schema version:** 1.2
**Type:** Markdown reference for AI agents (producer + consumer)

> **v1.2 (minor, backward-compatible):** thêm section `[REUSE AUDIT]` (bằng chứng matching per-control — producer Stage 4b bắt buộc sinh; consumer warn-nếu-thiếu, không reject), field `Reuse rejection` cho item `[NEW]` (producer bắt buộc; consumer warn-nếu-thiếu), warning type `WCAG_CONTRAST_FAIL` (consumer warning-blocker block khi PENDING).

> **Scope per-DS (multi-DS):** proposal/report nằm trong `feature_deltas/` của DS root tương ứng unit (`{family}/{ds_id}/feature_deltas/{id}/`). Producer ghi thêm dòng `ds_id: {ds_id}` vào header khi project có `registry.yaml` — audit trail phân biệt DS. "repo-wide" trong bootstrap_report = phạm vi 1 DS/1 repo, không phải toàn project.

**Used by:**
- **Producer** — Stage 4b `/ntapp-ui-generation` Agent 1 (Design System Architect) → ghi `proposed_ds_updates.md` cho mỗi `screen_id` / `widget_id`.
- **Producer** — `/ntapp-ds-bootstrap` → ghi `bootstrap_report.md` (one-time, repo-wide, không có `id` đi kèm).
- **Producer** — Manual mode: DSO viết tay theo template (non-BMAD repo).
- **Consumer** — `/ntapp-ds-build-component` (parse delta để build code thật).

---

## 1. Mục đích

Chuẩn hoá format Markdown của file proposal mà producer sinh ra để consumer parse được không cần đoán format. File này là **interface contract** — producer và consumer thay đổi độc lập, miễn còn tuân thủ schema.

## 2. Vị trí và đặt tên file

| Mode | Path (template) | Naming |
|---|---|---|
| BMAD Stage 4b (per FE unit) | `{design_system_root}/feature_deltas/{id}/proposed_ds_updates.md` | `proposed_ds_updates.md` (singular, `{id}` = `screen_id` / `widget_id`) |
| Bootstrap (one-time, repo-wide) | `{design_system_root}/bootstrap_report.md` | `bootstrap_report.md` (singular) |
| Manual mode (non-BMAD) | path từ config `proposal_file` | `<proposal_id>.md` |

Mọi path đọc từ `.bmm-config.yaml`. KHÔNG hardcode trong skill.

> **Lưu ý naming:** Không có file `design_system_report_*.md` — đó là tên cũ đã bị thay thế. Producer Stage 4b ghi `proposed_ds_updates.md` per-unit, producer bootstrap ghi `bootstrap_report.md` repo-wide.

## 3. Cấu trúc tổng thể

```
# Design System Delta Report — {id}

> Front matter (blockquote)

## [NEW]
  ### Item 1
  ### Item 2

## [MODIFIED]
  ### Item 1

## [WARNINGS]
  ### Warning 1

## [REUSE AUDIT]   ← v1.2, producer Stage 4b bắt buộc; consumer warn nếu thiếu
  | control_id | Top-3 candidates (score) | Decision | Reuse rejection |

## [SUMMARY]   ← optional, build skill tự sinh nếu thiếu
```

> **Backward compat với Stage 4b Agent 1:** Agent 1 hiện output 4 section gốc (`[NEW COMPONENTS/TOKEN]`, `[TYPE(TOKEN/COMPONENT)]`, `[MODIFIED COMPONENTS]`, `[ARCHITECTURAL WARNINGS]`). Parser của consumer chấp nhận cả 2 dạng theo regex (xem mục 9):
> - `[NEW COMPONENTS/TOKEN]` ↔ `[NEW]`
> - `[MODIFIED COMPONENTS]` ↔ `[MODIFIED]`
> - `[ARCHITECTURAL WARNINGS]` ↔ `[WARNINGS]`
> - `[TYPE(TOKEN/COMPONENT)]` KHÔNG là section riêng — luôn parse như field bắt buộc trong item của `[NEW]`.

## 4. Front matter

Đặt ngay sau H1 title, dạng blockquote. Field bắt buộc:

```markdown
> **Generated by:** <agent-name-or-DSO-name> | **Date:** YYYY-MM-DD
> **Source:** <input-file-path-or-description>
> **Schema version:** 1.1
> **Scope:** <id> (screen_id / widget_id) | <proposal_id> | "repo-wide"
```

Field optional:
- `Master DS version:` — bản `master_token.json` đang reference
- `Stack:` — framework profile (`angular`, `react`, ...)

Consumer dùng front matter để: (a) validate schema version, (b) trace nguồn lỗi, (c) map đúng `id` của đơn vị work.

## 5. Section `[NEW]` — items mới

### 5.1 Format chung mỗi item

```markdown
### <kebab-case-name>
- **TYPE:** COMPONENT | TOKEN
- **Source ref:** <L3-section-id-or-description>
- **Rationale:** <lý do cần>
- (fields tiếp theo phụ thuộc TYPE — xem 5.2 và 5.3)
```

### 5.2 TYPE: COMPONENT — fields

| Field | Required | Mô tả |
|---|---|---|
| `Name` (H3) | ✅ | kebab-case, unique trong `components_metadata.json` |
| `TYPE` | ✅ | `COMPONENT` |
| `Semantic intent` | ✅ | 1-2 câu mô tả mục đích (dùng cho retrieval semantic search) |
| `Variants` | ✅ | list (vd: `primary, secondary`). `none` nếu không có. |
| `States` | ✅ | list (vd: `idle, hover, disabled, loading`). |
| `Inputs/Props` | ✅ | name + type cho mỗi prop |
| `Outputs/Events` | optional | name + payload type |
| `Accessibility` | recommended | role, aria-*, keyboard nav requirements |
| `Library primitive` | optional | nếu nên wrap (vd: `p-progressbar` của PrimeNG) — guideline cho scaffolder |
| `Source ref` | ✅ | path tới L3 section hoặc description |
| `Rationale` | ✅ | tại sao DS hiện chưa đủ |
| `Reuse rejection` | ✅ (v1.2, producer 4b) | vì sao KHÔNG reuse: liệt kê từng candidate score ≥0.50 + recipe đã xét kèm lý do loại. Consumer warn nếu thiếu (không reject — backward compat proposal cũ) |

**Ví dụ:**

```markdown
### progress-bar
- **TYPE:** COMPONENT
- **Source ref:** ING_05_PROG_01 (L3 Section 2.3)
- **Semantic intent:** Hiển thị tiến độ upload file dạng linear progress với label %.
- **Variants:** linear, circular
- **States:** idle, uploading, success, error
- **Inputs:**
  - `value: number (0-100)`
  - `label?: string`
  - `variant?: 'linear' | 'circular'`
- **Outputs:** none
- **Accessibility:** role="progressbar", aria-valuenow, aria-valuemin=0, aria-valuemax=100
- **Library primitive:** PrimeNG `p-progressbar` (wrap, không build from scratch)
- **Rationale:** L3 ING_05 yêu cầu visual feedback upload, hệ thống chưa có component progress.
```

### 5.3 TYPE: TOKEN — fields

| Field | Required | Mô tả |
|---|---|---|
| `Name` (H3) | ✅ | path đầy đủ trong `master_token.json` (vd: `semantic.color.action.tertiary`) |
| `TYPE` | ✅ | `TOKEN` |
| `Tier` | ✅ | `global` \| `semantic` \| `component` |
| `Category` | ✅ | `color` \| `spacing` \| `typography` \| `shadow` \| `z-index` \| `breakpoint` \| `radius` |
| `Value` | ✅ | giá trị raw hoặc reference `{path.to.token}` |
| `Source ref` | ✅ | path tới L3 hoặc raw value gặp trong code |
| `Rationale` | ✅ | tại sao cần token này |

**Ví dụ:**

```markdown
### semantic.color.action.tertiary
- **TYPE:** TOKEN
- **Tier:** semantic
- **Category:** color
- **Value:** `{global.color.scarlet.400}`
- **Source ref:** ING_05 button "Re-upload" — hex `#ff6d73` xuất hiện trong DD
- **Rationale:** Cần variant thứ 3 cho action button, hiện chỉ có primary và secondary.
```

## 6. Section `[MODIFIED]` — sửa item đã có

### Format mỗi item

```markdown
### <existing-component-or-token-name>
- **Change type:** ADD_STATE | ADD_VARIANT | ADD_PROP | EXPOSE_PRIMITIVE_PROP | UPDATE_TOKEN_VALUE | DEPRECATE
- **Detail:** <mô tả change>
- **Breaking change:** YES | NO
- **Migration note:** <nếu YES, hướng dẫn migrate; nếu NO, viết "N/A">
- **Source ref:** <L3 hoặc raw>
- **Rationale:** <lý do>
- **Primitive prop ref:** (chỉ cần khi change_type = EXPOSE_PRIMITIVE_PROP) — `<library>@<version>.<Component>.<prop>` (vd `antd@5.12.0.Button.shape`)
```

### Change types

| Change type | Nội dung | Khi nào dùng |
|---|---|---|
| `ADD_STATE` | Thêm state mới vào abstract.states | UX yêu cầu state mới (vd: thêm `hovering` cho dropzone) |
| `ADD_VARIANT` | Thêm variant string vào abstract.variants | Variant hoàn toàn mới, KHÔNG mapping được sang prop của primitive |
| `ADD_PROP` | Thêm input mới vào abstract.inputs (custom prop của wrapper) | Wrapper cần behavior mới không phụ thuộc primitive |
| `EXPOSE_PRIMITIVE_PROP` | Forward prop từ primitive lib lên wrapper (vd: vt-button expose antd Button.shape) | (v1.1+) Stage 4b Agent 1 detect nhu cầu khớp prop có sẵn của primitive — ưu tiên expose thay vì tạo variant custom với CSS |
| `UPDATE_TOKEN_VALUE` | Đổi value của token reference trong tokens_used | Re-skin component theo brand update |
| `DEPRECATE` | Mark component status = deprecated | Component bị thay thế bởi component khác |

**Ví dụ:**

```markdown
### dropzone
- **Change type:** ADD_STATE
- **Detail:** Thêm state `HOVERING` (khi user kéo file vào nhưng chưa thả). Visual: border đậm + bg subtle.
- **Breaking change:** NO
- **Migration note:** N/A — additive change, không phá API hiện tại.
- **Source ref:** ING_05_PROG_01 L3 Section 2.4
- **Rationale:** UX requirement — user cần feedback khi file ở trên dropzone.
```

> **Breaking change = YES** kích hoạt extra check trong build skill: `component-patcher` PHẢI sinh migration note vào `build_report` và yêu cầu DSO co-approve riêng.

## 7. Section `[WARNINGS]` — cảnh báo

### Format mỗi warning

```markdown
### <warning-id-or-title>
- **Type:** FUNCTIONAL_DUPLICATE | NAMING_CONFLICT | TIER_VIOLATION | UNCLEAR_INTENT | WRAPPER_PROP_HIDDEN | STYLE_FRAGMENTATION | <khác>
- **Items:** <list các component/token liên quan>
- **Similarity:** <0.0-1.0>  ← optional, cho FUNCTIONAL_DUPLICATE
- **Primitive prop:** (chỉ cần cho WRAPPER_PROP_HIDDEN) — `<library>@<version>.<Component>.<prop>` reference
- **Recommendation:** <DSO nên làm gì>
- **Resolution status:** PENDING | RESOLVED | OVERRIDDEN
- **Resolution note:** <DSO ghi gì khi resolve>
```

### Warning types

| Type | Khi nào | Mặc định action |
|---|---|---|
| `FUNCTIONAL_DUPLICATE` | 2 component khác tên cùng chức năng (toast vs banner) | Consolidate, deprecate 1 |
| `NAMING_CONFLICT` | Tên trùng / gây nhầm lẫn | Rename trước khi build |
| `TIER_VIOLATION` | Token reference ngược tier (semantic → component) | Reject, sửa proposal |
| `UNCLEAR_INTENT` | `semantic_intent` chung chung / không actionable | DSO viết rõ intent |
| `WRAPPER_PROP_HIDDEN` (v1.1+) | Wrapper component (vd `vt-button`) giấu prop có sẵn ở primitive (vd `antd Button.shape`). Phát hiện khi component-discoverer diff wrapper API vs primitive_api | Propose `[MODIFIED]` change_type `EXPOSE_PRIMITIVE_PROP` để forward prop lên wrapper |
| `STYLE_FRAGMENTATION` | Cùng primitive bị fragment style. Hai dạng: (a) **per-screen** — cùng component class dùng ở nhiều screen với style khác nhau (vd 1 wrapper xài radius `X` ở screen A và `Y` ở screen B); (b) **per-wrapper** — nhiều wrapper khác nhau cùng wrap 1 primitive nhưng resolve cùng style property qua giá trị / token khác nhau (vd wrapper-A `border-radius: <value-X>`, wrapper-B `border-radius: <value-Y>` cùng wrap primitive `<P>`). Phát hiện dạng (b) bởi `/ntapp-ds-bootstrap` Rule 4.14 (xem `best-practices.md`) | DSO quyết định consolidate (single `component.<primitive>.<property>` token) hoặc add variant chính thức |
| `WCAG_CONTRAST_FAIL` (v1.2) | Cặp fg/bg trong proposal (token mới hoặc component variant/state) đo contrast < WCAG AA (4.5:1 text / 3:1 large+UI — công thức owned bởi `best-practices.md`). Producer: Stage 4b Step 1 Stage 3.4 contrast pre-check. Fields bắt buộc: `Pair` (2 token paths), `Ratio` (đo được), `Required` (ngưỡng), `Suggested fix` (token thay thế) | **Block** (warning-blocker severity high) — DSO đổi token/value cho đạt AA rồi set RESOLVED; override phải kèm legal/accessibility note |

**Ví dụ:**

```markdown
### Functional duplicate: Toast vs NotificationBanner
- **Type:** FUNCTIONAL_DUPLICATE
- **Items:** Proposed `Toast`, Existing `NotificationBanner`
- **Similarity:** 0.78
- **Recommendation:** Cân nhắc extend `NotificationBanner` thay vì tạo `Toast` mới.
- **Resolution status:** PENDING
- **Resolution note:** (DSO điền)
```

```markdown
### Wrapper hidden prop: vt-button.shape
- **Type:** WRAPPER_PROP_HIDDEN
- **Items:** Wrapper `vt-button` (custom Angular), Primitive `antd@5.12.0.Button`
- **Primitive prop:** `antd@5.12.0.Button.shape` (enum: default | circle | round, tier_hint: radius)
- **Recommendation:** Wrapper đang giấu prop `shape` của primitive. Khi screen mới cần button bo tròn lớn (pill), ưu tiên propose `[MODIFIED] vt-button` với `change_type: EXPOSE_PRIMITIVE_PROP` (forward `shape` lên wrapper) thay vì tạo `[NEW] button-pill` variant với CSS custom.
- **Resolution status:** PENDING
- **Resolution note:** (DSO điền)
```

> **Build skill xử lý theo `Resolution status`:**
> - `PENDING` → exit code = 1, **block** workflow.
> - `RESOLVED` → bỏ qua warning, **không build** item liên quan (DSO đã quyết dùng existing).
> - `OVERRIDDEN` → tiếp tục build item liên quan, log override vào `build_report` để audit.

## 8. Section `[SUMMARY]` — auto-computed

DSO **không phải viết tay**. Build skill tự generate. Stage 4b Agent 1 phiên bản tương lai cũng có thể tự sinh.

```markdown
## [SUMMARY]
- New components: <count>
- New tokens: <count>
- Modified components: <count>
- Warnings: <pending-count> pending / <total> total
- **Build skill action:** REQUIRED | OPTIONAL | BLOCKED | NONE
- **Hard gate:** YES | NO
- **Master DS version target:** v<N+1>
```

**Logic:**

| Tình huống | `Build skill action` | `Hard gate` |
|---|---|---|
| Có ≥1 NEW COMPONENT | REQUIRED | **YES** ← workflow STOP, build phải chạy + duyệt trước Stage 5 |
| Có ≥1 MODIFIED component | REQUIRED | NO |
| Chỉ có NEW TOKEN | OPTIONAL (build skill chỉ update master_token.json) | NO |
| Có ≥1 WARNING với status PENDING | BLOCKED | YES |
| Mọi section empty | NONE | NO |

## 9. Parsing contract — cho consumer

Consumer parse file theo regex sau (case-insensitive, parse-tolerant):

```
H1 (^# .+):                                    title, extract scope id
H2 (^## .+):
  r'\[NEW( COMPONENTS?\s*/?\s*TOKENS?)?\]'    → section NEW
  r'\[MODIFIED( COMPONENTS?)?\]'               → section MODIFIED
  r'\[(ARCHITECTURAL )?WARNINGS?\]'            → section WARNINGS
  r'\[REUSE AUDIT\]'                           → section REUSE_AUDIT (v1.2, optional cho parser)
  r'\[SUMMARY\]'                               → section SUMMARY
H3 (^### .+):                                  item identifier
Bullet (^- \*\*<Field>:\*\*\s*<value>):       field-value pair
```

**Consumer rules:**
- ❌ Reject nếu thiếu front matter required fields.
- ❌ Reject nếu schema version không tương thích (xem mục 10).
- ❌ Reject (exit 1) nếu item NEW thiếu field required theo TYPE.
- ⚠️ Warn (không reject) nếu item thiếu field optional.
- ⚠️ Warn nếu gặp section `[TYPE(TOKEN/COMPONENT)]` ở H2 (Agent 1 cũ) — bỏ qua section đó, parse `TYPE` từ field trong items.

## 10. Versioning

Schema này dùng **semver-like**:

| Bump | Khi nào | Backward compat |
|---|---|---|
| **Major** (1.0 → 2.0) | Đổi cấu trúc parsing (rename section, đổi format field) | ❌ Consumer phải update |
| **Minor** (1.0 → 1.1) | Thêm field optional, thêm enum value mới | ✅ |
| **Patch** (1.0.0 → 1.0.1) | Sửa typo, làm rõ wording | ✅ |

Producer **bắt buộc** khai báo version trong front matter. Consumer check tương thích trước khi parse:
- Major khớp → parse OK.
- Major khác → reject với error rõ.

### <component-or-token-name>

## 12. Edge cases

| Case | Xử lý |
|---|---|
| Section thiếu hoàn toàn | Treat như empty. |
| Section có heading nhưng nội dung `(none)` hoặc rỗng | Treat như empty. |
| 2 item cùng `Name` trong `[NEW]` | Reject (exit 1). DSO sửa proposal. |
| Unicode/emoji trong `Name` | Reject. kebab-case ASCII only. |
| NEW TOKEN reference token chưa tồn tại | Reject. DSO phải thêm dependency token vào `[NEW]` trước (manual cascade — không auto). |
| MODIFIED component không tồn tại trong `components_metadata.json` | Reject. DSO clarify (có thể intent là NEW). |
| Front matter `Schema version` thiếu | Reject. |
